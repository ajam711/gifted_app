# Gift app — V1 contract

Private web app for exactly two people. Either person adds items to either list. Only the list owner reacts (liked / disliked). The other person claims from the liked pile and marks a gift given once it is handed over; it then moves to the owner's Received list. Given and received items stay as history so gifts are not repeated later.

## Secrecy rule

The list owner must never observe claims on their own items — not in the UI, not in an API payload, not in counts, not in response size. Claim / giver-note data is absent from owner views, not hidden with CSS. Owner payloads are identical before and after a claim (same ids, same count).

The one reveal is hand-over. When the shopper marks a gift given, they are confirming the owner has it in their hands, so the item moves to the owner's Received list with who gave it. The confirm step says so before the shopper commits. Nothing about a claim reaches the owner before that.

The owner can also record a gift received from someone else. That is the owner reporting what they already know, so it reveals nothing: the owner's response is identical whether or not the item was claimed. A claim on it is released and the shopper is told.

The shopper *is* allowed to know claim state. Shopper-action refusals name the reason (“you already claimed this”, “Ada no longer wants this”); the owner can never reach those messages because the actor is checked before the item's state.

## Loop

Add → React → Claim → Give (hand-over, confirmed) → Received, then it repeats. Standing list per person. Occasion is a nullable tag on the item, not a mode switch and not a List entity. Someone who never tags anything has a running list.

## Screens

Five screens. List identity for add-item is the list the screen was opened from, not a picker.

| Screen | Who | What |
|---|---|---|
| Home | both | Two doors (my list / their list), badges, quick add. |
| My list | owner | Pending reactions; liked and disliked in separate groups; Received (what, from whom, when), with “Got it elsewhere” on any item not yet received. No claim or giver-note data. |
| Their list | shopper | Yours (claimed, with a confirm step on Mark given); liked items to claim; waiting on the owner; “Not for <name>” (disliked, with a notice if a claim was released); “<name> already has” (received from someone else, with a notice if a claim was released); “Gifts given to <name>” history. |
| Add item | both | Name required. Link, price, tag, private note optional. Target: under ten seconds from open to saved. |
| Item detail | both | Same item, different fields by viewer (`OwnerItemView` vs `ShopperItemView`). |

Home badges:

- **“N need you”** — count of `needs_reaction` items on my list.
- **“Birthday in 12 days”** — next `ImportantDate` for the other person (label + days until). Lookup of “the other person” always goes through `Connection`.

## Not V1

Out of scope. Do not build, schema, or describe as current work:

- More than two people, groups, Secret Santa
- In-app checkout or payments (outbound links only)
- Native iOS / App Store
- Public signup, email verification, password reset (operator creates the two accounts)
- React / Vue / Svelte SPA
- Go backend
- A `List` table
- A `Claim` table or `Reaction` table
- A stored `status` column on items
- A settings screen that asks how the user “thinks about lists”

## Data model

Four domain tables. A list is `Item.owner_id = viewer`. Auth is adjacent (`django.contrib.auth.User` or equivalent), not a second gift-domain user table. `Person` does not store a password hash.

### Person

| Column | Notes |
|---|---|
| id | PK |
| name | display |
| email | |

### Connection

Exactly one pair. Every “other person” lookup goes through this table. Application code never infers the partner by counting `Person` rows.

| Column | Notes |
|---|---|
| person_a_id | FK → Person |
| person_b_id | FK → Person |
| created_at | |

Constraints:

- `CHECK (person_a_id < person_b_id)`
- `UNIQUE (person_a_id, person_b_id)`

### ImportantDate

Drives Home badges. Recurring dates store month + day with `year` null. One-off events set `year`. Do not store a single calendar date that goes stale next year.

| Column | Notes |
|---|---|
| person_id | FK → Person |
| label | e.g. `"Birthday"` |
| month | 1–12 |
| day | 1–31 |
| year | nullable; set only for one-off events |

### Item

| Column | Notes |
|---|---|
| id | PK |
| owner_id | whose list |
| added_by_id | who created the row |
| name | required |
| url | nullable |
| price_text | nullable. Free text (`"around $120"`), not decimal / cents |
| tag | nullable free text (occasion or category). Not a table |
| giver_note | nullable. Shopper-only |
| reaction | nullable `'liked'` \| `'disliked'` |
| reacted_at | nullable |
| claimed_by_id | nullable. Shopper-only |
| claimed_at | nullable. Shopper-only |
| given_at | nullable. Shopper-only |
| claim_released_at | nullable. Shopper-only. Set when an owner dislike or “got it elsewhere” releases a claim; drives the shopper's notice |
| received_at | nullable. Set by the shopper's give (same instant as `given_at`) or by the owner's “got it elsewhere”. Owner-visible |
| received_from | nullable free text. Who it came from when the owner records it as received elsewhere (“Grandma”). Owner-visible |
| created_at | |

When the owner adds to their own list, persist `reaction='liked'` (and `reacted_at`) in the same insert. `reaction IS NULL` has one meaning: partner suggestion waiting on yes/no.

No `List` table. No `Claim` table. No `Reaction` table. No stored `status` column.

### Derived states (never stored)

| State | Predicate |
|---|---|
| `needs_reaction` | `added_by_id != owner_id AND reaction IS NULL AND received_at IS NULL` |
| `liked_open` | `reaction = 'liked' AND claimed_by_id IS NULL AND received_at IS NULL` |
| `claimed` | `claimed_by_id IS NOT NULL AND given_at IS NULL` |
| `given` | `given_at IS NOT NULL` (always also received) |
| `received` | `received_at IS NOT NULL` |
| `received_elsewhere` | `received_at IS NOT NULL AND given_at IS NULL` |
| `disliked` | `reaction = 'disliked'` |

### Viewer projection

Shopper-only fields — omit from owner payloads entirely (keys absent, not null, not CSS-hidden):

`giver_note`, `claimed_by_id`, `claimed_at`, `given_at`, `claim_released_at`

Owner view may include: `name`, `url`, `price_text`, `tag`, `added_by`, `created_at`, `reaction`, `received_at`, `received_from`, and `received_from_id` — the giver's id, which is `claimed_by_id` *only when `given_at` is set* and null otherwise. It is the hand-over reveal and nothing earlier.

Two view types. Do not merge a dict that can grow a secret field onto a shared base.

```python
class OwnerItemView:
    id: int
    name: str
    url: str | None
    price_text: str | None
    tag: str | None
    added_by_id: int
    created_at: datetime
    reaction: Literal["liked", "disliked"] | None
    received_at: datetime | None
    received_from_id: int | None  # set only once given
    received_from: str | None

class ShopperItemView:
    id: int
    name: str
    url: str | None
    price_text: str | None
    tag: str | None
    added_by_id: int
    created_at: datetime
    reaction: Literal["liked", "disliked"] | None
    giver_note: str | None
    claimed_by_id: int | None
    claimed_at: datetime | None
    given_at: datetime | None
    claim_released_at: datetime | None
    received_at: datetime | None
    received_from: str | None
```

## Mutation rules

Partner means the other person via `Connection`. Refusals the owner can reach do not explain why. Refusals only the partner can reach name the reason.

| Action | Actor | Allowed when | Effect | Refusal |
|---|---|---|---|---|
| add | either person | `name` non-empty; `owner_id` is self or partner | Insert. If `added_by_id == owner_id`, set `reaction='liked'` and `reacted_at` in the same insert | Validation error |
| react | owner only | `owner_id == actor` (always, claimed or not) | Set `reaction` to `'liked'` or `'disliked'`; set `reacted_at`. `'disliked'` on a claimed, not-received item also clears `claimed_by_id`, `claimed_at` and sets `claim_released_at`. Any other reaction clears `claim_released_at`. Received items keep their claim and notice | Not owner → forbidden |
| claim | partner only | `liked_open`; actor is partner; actor ≠ owner | Set `claimed_by_id`, `claimed_at`; clear `claim_released_at` | Owner / stranger → forbidden. Partner → the reason (already yours, not liked yet, disliked, given). Never a payload the owner can see |
| unclaim | claimer only | `claimed_by_id == actor AND given_at IS NULL` | Clear `claimed_by_id`, `claimed_at` | Owner / stranger → forbidden. Partner → the reason |
| give | claimer only, after a confirm step that says the owner will see it | `claimed_by_id == actor AND given_at IS NULL` | Set `given_at` and `received_at`. The owner now sees it under Received, from the claimer | Owner / stranger → forbidden. Partner → the reason |
| receive | owner only | `received_at IS NULL` (claimed or not) | Set `received_at`; set `received_from` to the optional name. If claimed, also clear `claimed_by_id`, `claimed_at` and set `claim_released_at`. Owner response identical whether or not it released a claim | Not owner → forbidden. Already received, or name too long → generic invalid |
| unreceive | owner only | `received_at IS NOT NULL AND given_at IS NULL` (undo a “got it elsewhere”) | Clear `received_at`, `received_from`, `claim_released_at`. A released claim stays released | Not owner → forbidden. Given by the partner → generic invalid |
| delete | owner of the item | — | Delete the row | If refused because the item is claimed, the error is the same generic validation failure as any other invalid delete. It does not reveal a claim |

Invariants:

- Only the owner can react.
- Only the partner can claim, and only liked + unclaimed + not given.
- Owner cannot claim their own item.
- The owner can always change a reaction. Disliking a claimed, not-given item releases the claim; the owner's response is identical whether or not it did.
- Unclaim is allowed by the claimer if not yet given.
- Mark given is the claimer’s action, and it is the hand-over: the owner sees the item as received from the claimer from then on. There is no undo.
- Only the owner records a gift received from someone else, and only the owner undoes that.
- Owner payloads are identical before and after a claim (same ids, same count), and before and after a “got it elsewhere” on a claimed vs unclaimed item.
- Every save checks the item is unchanged since it was read; if it changed, the action is re-checked against the current row.
- Delete / validation errors must not reveal that an item was claimed.
- Received items leave the owner's pending, liked and disliked groups and show only under Received.

## Stack

V1 default:

- Python 3.14 (current stable)
- Django + Django templates + HTMX (Alpine only if a control needs client-only state)
- SQLite
- Session cookies, not JWT
- Tailwind or plain CSS — no frontend build step required
- Deploy later on Fly.io / Render / Railway
- Two accounts created in Django admin; no signup flow

Rejected for V1:

- **FastAPI** — a fine later rewrite if the learning goal is API-first Python; not V1.
- **React** — résumé-shaped complexity. The API/HTML will not care if it is added later.
- **Go** — a good second implementation of the same domain, not a second backend in V1.

Infra non-goals: no public signup, no email verification, no password reset. Operator creates the two accounts.
